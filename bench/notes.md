## Hotspots found and fixed

| Hotspot | Fix | Effect (numbers above) |
|---|---|---|
| GPU renderer created synchronously in `Core::open` (wgpu adapter init) | `LazyRenderer` creates it on a background thread; first render waits for the one shared init | cold start 400-500 ms to about 30 ms |
| `/api/photos` sorted complete 33-column rows for the whole session on every page | two-step query: sort `(id, key)` pairs with `LIMIT n+1`, then read the wide rows for those ids | page 2.5-4x faster at 20k, 4-6x at 100k rows in one session |
| Planner looped over `root_folder` first, scanning the session members once per root | pinned join order (`CROSS JOIN`), except for `burst_id` filters, which start from the burst index | included above; `COUNT(*)` no longer joins `root_folder` |
| `COUNT(*)` on every page | skipped when the page holds the whole result; otherwise cached per (query, catalog generation); the generation moves when any pooled connection changes a row (`total_changes`) | pages 2..n of a filter cost only the page; `limit=1` collection counts 2x faster |
| `tidy_json` middleware parsed and re-serialised every JSON body on an async worker; photo pages went through `serde_json::Value` first | byte-scan fast path (no parse when nothing needs tidying), heavy path on the blocking pool, photo pages serialised straight from the row structs, `ai_score` / `ai_rating` tidied at read | 5000-row page 75 to 28 ms, whole 20k pull 383 to 166 ms |
| Preference labels written one autocommit statement per photo, statements recompiled each time | one transaction, `prepare_cached` | PATCH of 20k photos 1213 to 122 ms |
| WebSocket coalescer merged `photos.updated` items with a linear search per item (O(n^2)) | id index | 20k updates reach the client in 155 ms instead of 759 ms |
| SQLite defaults | `cache_size` 32 MB per connection, `temp_store=MEMORY` (mmap was already on) | part of the sort and count gains |
| Loupe: every layer started transparent and faded in over 160 ms, even for preloaded photos | cached images are shown immediately, neighbours preloaded 3 ahead / 2 behind and decoded | next photo 180 ms to 6 ms |
| Grid cells each held an `i18next` subscription | `t` passed down as a prop | fewer janky frames when scrolling a dense grid on a slow CPU |
| Analysis progress was shown as an "Export finished" toast (found by the new real-server end-to-end test) | analysis tasks are not shown in the export toast list | UI bug fix |

## Not a problem at this scale

* **Import** of 1000 x 12 MP JPEG is already far inside the targets (first rows 25 ms, metadata for the first screen 84 ms, all thumbnails 1.5 s): thumbnails are generated by DCT-scaled decoding on all cores.
* **Thumbnail queue**: no contention seen; the 24 workers share 6 pooled connections and the writes are single small updates.
* **Grid scrolling** keeps 60 fps (16.7 ms p95) at 20k photos and up to 6000 px/s on the unthrottled run, with only about 20 cells mounted; the dense / 4x throttled case is the only one that drops frames.
* **Memory** stays below 100 MB for a 20k session (PRD: 1.5 GB excluding models).

## Remaining gaps

* **Single 100k-row session** (outside the PRD: 20k per session): pages cost about 10 ms and `-taken_at` 28 ms, because the session members still have to be visited to sort. An index that stores the sort key next to the session (a `session_photo(session_id, taken_at, photo_id)` table) would make every page O(limit); not done because it changes the schema and every write path.
* `rating_gte` on a single 20k session is slower than before (0.5 to 2.1 ms): the old plan used the rating index, which wins when almost nothing matches but lost badly (27 ms) at 100k rows.
* `GET /api/sessions` aggregates every member row of every session (13 ms at 100k rows); it is refetched on `session.updated`. Counters on the `session` table would remove it.
* Preview generation for 12 MP originals is 35 ms (1024) / 65 ms (2048) cold; the loupe hides it by preloading neighbours, but jumping to a far photo waits for it (the 256 px thumbnail shows meanwhile).
* Frame times come from headless Chromium with software rasterisation; a run on real GPU hardware with a real browser profile is still needed before calling the 60 fps target closed for dense grids on low-end laptops.
* The fake worker returns synthetic `fast` results only (no faces, embeddings, aesthetic scores), so the real-server end-to-end test does not cover the people views.
